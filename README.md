# parallel_request

Утилита делит один SQL-запрос на временные интервалы, выполняет чанки в
нескольких потоках и объединяет ответы в один `pandas.DataFrame`. Готовая точка
входа настроена на три сервера ClickHouse `THEATRE_RU`:

- `sv1-bfa-ch.travelline.wan:8123`;
- `mv1-bfa-ch.travelline.wan:8123`;
- `mv2-bfa-ch.travelline.wan:8123`.

База на каждом сервере — `BookingFormAnalyticsV2`.

Границы чанков имеют вид `[start_date, end_date)`: начало включается, конец не
включается. Благодаря этому соседние запросы не дублируют строки на границе.

## Быстрый старт

Нужен Python 3.10 или новее.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
```

Откройте `.env` и заполните свои реквизиты:

```dotenv
THEATRE_LOGIN_RU=your_login
THEATRE_PASS_RU=your_password
```

Одна пара реквизитов используется на всех выбранных серверах. Если `.env`
уже заполнен, менять или копировать его заново не нужно. Файл игнорируется Git
и не должен попадать в репозиторий.

Затем откройте `src/main.py`. В нём уже находится запрос выгрузки checkout и
диапазон дат. При необходимости измените:

- `QUERY` — SQL-запрос;
- `DATE_RANGES` — диапазоны, в которых обе указанные даты включаются;
- `CHUNK_TYPE` — размер чанка (`HOUR`, `DAY`, `WEEK`, `MONTH`, `QUARTER`, `YEAR`);
- `WORKERS` — общий максимум одновременно работающих воркеров на все серверы;
- `CLICKHOUSE_HOSTS` — выбранные серверы без протокола и порта (порт общий: `8123`).

Например:

```python
WORKERS = 3
CLICKHOUSE_HOSTS = [
    "sv1-bfa-ch.travelline.wan",
    "mv1-bfa-ch.travelline.wan",
    "mv2-bfa-ch.travelline.wan",
]
```

При достаточном количестве чанков 3 воркера создадут по одному подключению на
сервер; 6 воркеров — по два. При 4 воркерах первый сервер получит два подключения,
остальные — по одному. Это общий лимит, а не количество воркеров на каждом сервере.
Каждый воркер держит отдельный клиент и работает на закреплённом сервере.
Для подключения к одному серверу оставьте только его в `CLICKHOUSE_HOSTS`.

Фактическое количество воркеров ограничивается числом чанков. Текущие настройки
`MONTH` и `2026-05-01 — 2026-05-16` создают **один чанк**: он выполняется на первом
сервере, даже если `WORKERS = 3`. Размер чанка автоматически не уменьшается.
`WEEK` означает 7 дней от начала диапазона с укороченным последним чанком.

Список серверов используется для распределения нагрузки: каждый чанк отправляется
ровно одному воркеру, а не копируется на каждый сервер. На любом выбранном сервере
запрос должен иметь доступ к полному набору данных и нужным словарям для своего
интервала. Если серверы содержат разные части данных, такая схема сама по себе
не объединит эти части. Состав данных и права доступа проверяются отдельно.

В запросе обязательны оба служебных параметра без кавычек:

```sql
SELECT *
FROM your_table
WHERE created_at >= {start_date}
  AND created_at < {end_date}
```

Запуск:

```powershell
python src/main.py
```

Объединённый результат сохраняется в `result.csv` в кодировке UTF-8 с BOM,
удобной для Excel. Чанки добавляются в результат в порядке завершения без
дополнительной сортировки. Освободившийся воркер сразу забирает следующий чанк
из общей очереди, не ожидая другие серверы. Более быстрый сервер может обработать
больше чанков. Между отдельными элементами `DATE_RANGES` выполнение остаётся
последовательным.

В консоль выводятся фактическое количество воркеров, начало и завершение чанка,
сервер, номер воркера, время каждого диапазона и общее время. Например:

```text
Чанков: 16. Воркеров: 3 (общий лимит: 3).
Worker #1 | sv1-bfa-ch.travelline.wan:8123 | подключён
Chunk #1 начат | Worker #1 | sv1-bfa-ch.travelline.wan:8123 | Период: [2026-05-01 00:00:00, 2026-05-02 00:00:00)
Chunk #1 завершён за 0:00:20. Строк: 15487 | Worker #1 | sv1-bfa-ch.travelline.wan:8123
```

Если подключение или любой чанк завершается с ошибкой, новые чанки перестают
выдаваться воркерам. В `stderr` выводится заметный блок с сервером, номером
воркера, номером чанка и диапазоном дат (для ошибки чанка), типом и текстом
исключения. Уже выполняющиеся запросы могут завершиться; процесс завершится
с ненулевым кодом. Частичный результат не сохраняется вместо успешной выгрузки.
Автоматического переноса упавшего чанка на другой сервер нет.
Сообщение `Chunk #... завершён` выводится только после успешной загрузки.

После последнего чанка каждый воркер выводит сообщения о начале и завершении
закрытия соединения. Затем появляются сообщения об объединении DataFrame и
сохранении CSV. Успешная загрузка всех чанков ещё не означает, что файл записан:
окончание выгрузки подтверждается строкой `Результат сохранён в: ...`.

При Ctrl+C выдача новых чанков останавливается. Уже запущенные запросы должны
закончиться (или завершиться по таймауту подключения/ответа), после чего соединения
закрываются, а процесс выходит с кодом `130`. Ctrl+C не отправляет серверу команду
отмены запроса. Сообщение об остановке выводится сразу, чтобы это ожидание было видно.

## Проверка проекта

```powershell
python -m compileall -q src tests
python -m unittest discover -s tests -v
```

Тесты используют подставные реквизиты и подключения: `.env` не читается,
запросы на настоящие серверы не отправляются.

Реальная скорость зависит от базы и общей инфраструктуры серверов.
`WORKERS` задаёт параллелизм клиента; число потоков выполнения одного запроса
внутри ClickHouse эта настройка не меняет.

## Исследование скорости и HTML-отчёт

`clickhouse-benchmark.html` — автономный интерактивный отчёт, открывается без
интернета. Исходные семь замеров сохранены в `benchmarks/historical.json`.
Лог за май–август хранится отдельно и не участвует в сравнении периода 1–16 мая.

`benchmarks/run_benchmarks.py` извлекает только строку `QUERY` из `src/main.py`
без импорта и запуска `main.py`. Период всегда **01–16.05.2026 включительно**.
Скрипт использует обычный механизм извлечения, но не сохраняет и не просматривает
строки результата: пишет только времена, границы чанков, серверы, воркеры,
статусы и счётчики строк в `benchmarks/runs/*.json`.

```powershell
python benchmarks/run_benchmarks.py --plan
python benchmarks/run_benchmarks.py --repeat 2
python benchmarks/build_report.py
```

По умолчанию реквизиты берутся только из переменных окружения
`THEATRE_LOGIN_RU` / `THEATRE_PASS_RU`; `.env` не открывается.
Опция `--use-env-file` разрешает загрузку `.env` самим скриптом, только если
владелец разрешил это явно. Значения не выводятся.
Можно ограничить матрицу через `--cases` (список имён показывает `--plan`).
Сценарии выполняются по очереди, максимум 6 одновременных запросов в текущей
матрице; при первой ошибке серия останавливается. Текст исключения скрыт,
поскольку драйвер может включать в него SQL или данные; сохраняется тип ошибки.
Проверку под реальной дневной нагрузкой следует проводить отдельно.
